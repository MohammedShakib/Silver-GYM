# Silver GYM Notification System

## 1. Overview
The Notification System orchestrates communication across Silver GYM for Members, Partners, and Admins. It follows an event-driven architecture, ensuring core business actions (e.g. payment processing, check-ins) remain decoupled from notification delivery.

## 2. Event Architecture & Outbox
Domain services do not send emails or create notifications directly. Instead, they write to the `DomainEventOutbox` table. 

- **DomainEventOutbox**: A database-backed reliable queue that holds business events (e.g., `PAYMENT_SUCCESSFUL`).
- Transactions writing business data (like marking a payment successful) also write the outbox event in the same transaction. This ensures guaranteed delivery of notifications without holding up the user request.

## 3. Notification Models
### Notification
Represents an individual message (in-app).
- `userId`: Recipient.
- `type`: E.g., `PAYMENT_SUCCESSFUL`.
- `category`: E.g., `PAYMENT`.
- `title`, `message`: Content of the notification.
- `actionUrl`: Deep link to the relevant page.
- `readAt`: Timestamp when the user read the notification.

### NotificationDelivery
Represents an attempt to deliver a notification via a specific channel.
- `channel`: `EMAIL`, `IN_APP` (In-app logic primarily relies on the Notification record, but Delivery tracks external channels).
- `status`: `QUEUED`, `PROCESSING`, `SENT`, `FAILED`, `SKIPPED`.
- `provider`: E.g., `RESEND`, `DEV`.

## 4. Channels & Providers
- **IN_APP**: Handled by fetching the `Notification` records from the frontend.
- **EMAIL**: Delivered via the `EmailProvider` interface.

## 5. Notification Preferences
Users can control what optional communications they receive.
- `NotificationPreference` Model stores boolean flags for `checkInEmail`, `paymentEmail`, etc.
- Critical security or transactional emails bypass preferences.

## 6. Worker & Retry Policy
The `NotificationWorker` is a background job that:
1. Polls `DomainEventOutbox` to process pending events into notifications and email delivery queues.
2. Polls `NotificationDelivery` to send queued emails.
3. Implements exponential backoff for retries on failure (up to `NOTIFICATION_MAX_RETRIES` times).
4. Marks delivery as `FAILED` if max retries are exceeded.

## 7. Deduplication
Idempotency is maintained via the `dedupKey` in the `DomainEventOutbox`. Duplicate events will not create multiple notification records.

## 8. Scheduled Notifications (Reminders)
Scheduled notifications (like renewal reminders) are generated by scheduled jobs that insert specific events into the `DomainEventOutbox` with future `nextAttemptAt` times or via dedicated cron tasks scanning the database.

## 9. Retention
By default, old in-app notifications can be paginated. A cleanup job (to be implemented) can archive notifications older than 6 months if needed.
